### Findings that shape the design

1. **Line endings follow the operating system.** `Files.write` uses the platform separator: the probe's reports on Windows end lines with CRLF; the pipeline (Linux) writes LF. A byte comparison would fail across machines for no business reason. The compare should normalise line endings (proposed default), and the ledger records it once.
2. **The rejection message contains the JDK's own text.** `(For input string: "notanumber")` is `NumberFormatException`'s message, not the application's. It is the same on JDK 17 today, but it is a platform source of difference, not the change's.
3. **Re-running the same business date "has not been verified"** (README section 5). Each reference run should start from an empty HBase (a fresh container in the pipeline) and use the three dates once.
4. **An empty report is the failure to catch.** A report of the header alone must fail the compare (brief AC4; the estate brief's Spark 3 trial wrote 0 rows with every unit test green).
5. The pipeline already starts HBase 1.4 in Docker on JDK 8 with the `host.docker.internal` hosts entry, so a capture-and-compare step fits in job `jdk8` after `mvn -B test` with no new service. The Spark cluster image (`salesbatch-runtime`) is not built in the pipeline today.

### Design (on the proposed defaults)

- **Capture** (`scripts/reference/capture.sh`, bash, runs on the pipeline's Linux runner and in Git Bash): after `mvn -B test` in job `jdk8` (HBase 1.4 already up in Docker), build the Spark classpath file (`mvn -B -DskipTests package dependency:build-classpath -Dmdep.outputFile=target/local-classpath.txt`), start `LocalDebugServer` from workflow-app's test classes with `-Dreport.dir=<out>/reports`, `-Dserver.port=18081` and the default `spark.mode=local-jvm`; wait for the port; for each of the three files `POST /batches`, poll `GET /batches/{id}` (time limit) until `WAITING_APPROVAL` or `FAILED`, approve when waiting; write `<out>/outcome-<file>.txt` (final status, error text, report present yes or no); stop the server. No source change: the debug server and the local Spark launcher already exist in the test sources.
- **Reference** (`docs/reference/`): the two reports as the capture wrote them on Linux, `sales-bad.outcome.txt`, and `README.md` (where they came from: the commit and pipeline run; how to regenerate in the pipeline and on Windows plus Docker in WSL, README sections 3 and 4).
- **Compare** (`scripts/reference/AC4_compare_with_reference.sh`): runs the capture into a fresh folder, then for each report: exists, has at least one data row, and equals the reference line for line after removing carriage returns; for `sales-bad.csv`: status and error text equal the recorded ones and no `report-<its date>.csv` exists. Exit 1 with the first difference printed. Uses the three dates once on a fresh HBase container (Assess finding 3).
- **Pipeline**: one step in job `jdk8` after `mvn -B test`: `bash scripts/reference/AC4_compare_with_reference.sh`; capture output uploaded as an artifact (`reference-run-jdk8`) on every run, so a person can read what a red run produced. Job `jdk17` is left as it is (it cannot build yet).
- **Where the reference comes from**: the card's branch has no change under `src/` (AC5), so its code is `main`'s 01b93f8; the capture runs on the branch's first pipeline run with the capture script, its artifact is committed into `docs/reference/`, and `README.md` names both commits and the run.
