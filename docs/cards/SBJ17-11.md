### What the change would really do (side-by-side)

Two runs, because the job has two halves: the aggregation (pure Spark) and the HBase read and write around it.

**1. Through the real stack, in the pipeline.** A trial commit on a scratch branch, `trial/SBJ17-11-spark35` (commit 1330789: `spark.version` 3.5.5, `scala.version` 2.12.18, `scala.binary.version` 2.12, nothing else; Assess only, never for merge), run [46007292373](https://github.com/ankursingh119/javapoc1.8/actions/runs/46007292373). Both jobs fail, against main's run 46003520665 where both pass:
- Job "JDK 8": spark-job 6 of 7 pass; `SalesAggregatorHBaseTest.jobAggregatesOnlyTheRequestedDate:89 expected:<2> but was:<0>`. The job logs `SalesAggregator finished for 20990101: 0 aggregate rows written`, with no exception: it read no rows from `sales_raw`. `install` stops, so the reference compare never runs in that job.
- Job "JDK 17": the production server runs the new Spark job (on JDK 8) on the three sample files. `sales-20261113.csv` ends **COMPLETED with a report that has the header and no rows**; the same for 20261115. `sales-bad.csv` is rejected as before. Artifacts: scratch `trial-run/`.
- **Group: the HBase read returns nothing, silently.** Inputs 3 (the sample files), differences 2 (both good files), one example above. A user would see a finished batch with an empty report. The pipeline's checks caught it (the HBase end-to-end test and the reference compare): the guards work.
- What changed underneath (`mvn dependency:list` on spark-job, old against new; `deps-old.txt`, `deps-new.txt`): Spark 3.5 brings **ZooKeeper 3.6.3** at compile scope in place of 3.4.6 (it would be shaded into the job jar beside the HBase 1.4.13 client; the log shows `Received event is not valid: Closed` from HBase's ZooKeeper watcher), and **Hadoop 3.3.4** (`hadoop-client-api`, `hadoop-client-runtime`) beside the provided Hadoop 2.10.1. Likely causes, for Plan to settle: the HBase 1.4 `TableInputFormat` on Hadoop 3 finding no splits or no rows, or the ZooKeeper 3.6 client with HBase 1.4. Not yet proved which.

My judgement: that reason is a false alarm, shown false. The tool's import scan does not see Scala tests in the same package, nor the pipeline's end-to-end checks. The trial run above is the discrimination test: the bare version bump broke the HBase read, and `SalesAggregatorHBaseTest`, the reference compare in the JDK 17 job and `scripts/java17/acceptance/AC2` all turned red. So the covering checks would notice a break, and they did. **Verdict: proceed with review.** The trial shows the change is more than a version bump: the build must also align the HBase client with what Spark 3.5 brings, and the pipeline proves it.

### Slice

One slice. INVEST:
- Independent: merges alone on main; the pipeline runs the job on its own Spark (`local[*]`). Production use waits on the cluster (risk below), which does not stop the merge.
- Negotiable: how the HBase client is aligned (pin ZooKeeper, exclude Hadoop 3 jars, or another way) is open for Plan.
- Valuable: removes Spark 2.4 and Scala 2.11, both end of life, from the job, the last module still tied to them.
- Estimable: done is the whole pipeline green with the reference reports unchanged; a few hours of agent time.
- Small: parent `pom.xml` versions, `spark-job/pom.xml` exclusions or pins, `docker/Dockerfile`, the README lines and script comments listed above: well under 400 lines, one pull request, a roadmap of about four steps (versions, HBase client alignment, local Spark cluster image, words).
- Testable: the existing HBase end-to-end test, the reference compare (`docs/reference/`) and the in-process harness above.
A split was weighed: aligning the HBase client cannot be done first on Spark 2.4, because the clash comes with Spark 3.5. The local Docker Spark cluster image could be its own card, but leaving it on Spark 2.4 would break the local cluster mode on main, so it stays in.

### Decisions for Plan, each with my proposed default

1. **Which Spark cluster the job is for.** The job jar does not bundle Spark, so a Spark 3.5 and Scala 2.12 jar will not run on EMR 5.36 (Spark 2.4, Scala 2.11). Default: this card moves the build, the pipeline and the local Docker cluster to Spark 3.5; moving the production cluster (an EMR release with Spark 3.5) is a separate decision before any release. Raised as a risk on the card.
2. **Which HBase client the job bundles.** Default: keep the HBase 1.4.13 client (the server in Docker, and on EMR 5.36, is HBase 1.4) and make it work beside Spark 3.5 by aligning ZooKeeper and Hadoop; an HBase 2 client is its own card, with the cluster move.
3. **An empty read finishes as COMPLETED.** The trial showed the job writing zero rows without failing, so a batch with data ends with an empty report. Default: keep today's behaviour in this card (behaviour kept, the pipeline checks guard it); a check that fails the job when raw rows exist and none are read can be its own card.

Versions I choose myself (standing answer SA-3): Spark 3.5.5 and Scala 2.12.18, as in the trial, unless Plan finds a reason for another 3.5 patch.
