### What the change would really do (side-by-side, through the real stack)

Nothing else changed: no JVM flags, class files still Java 8.

Run [46117305017](https://github.com/ankursingh119/javapoc1.8/actions/runs/46117305017), against main's run 46116037965:
- JDK 8 job: unchanged, success, 68 of 68.
- JDK 17 job: the whole reactor **builds** on JDK 17 (Scala 2.12.18 and javac fine). Tests: common 30 of 30, **spark-job 3 of 8 (5 in error)**, workflow-app 30 of 30, so **63 of 68** on JDK 17.
- Side-by-side summary: inputs 3 sample files plus the 8 spark-job tests; environments JDK 8 and JDK 17; **differences: 3 groups**.
  1. **Spark does not start on JDK 17 without module access.** `SalesAggregatorTest.start`: `IllegalAccessError: class org.apache.spark.storage.StorageUtils$ cannot access class sun.nio.ch.DirectBuffer (module java.base does not export sun.nio.ch to unnamed module)`. Spark 3.5 needs the `--add-opens`/`--add-exports` list it ships (`JavaModuleOptions`) on any JVM that is not started by `spark-submit`: the surefire JVM here.
  2. **The HBase-backed spark-job tests cannot reach ZooKeeper on JDK 17.** `SalesAggregatorHBaseTest` (4) and `AC2SmallRegionIsReadTest` (2): `KeeperErrorCode = ConnectionLoss for /hbase` in `setUp`, while the same HBase container serves the JDK 8 job's same tests. Cause not yet known; first suspects: the module-access failure above leaving the shared JVM in a bad state, or the ZooKeeper client in the spark-job test classpath (Hadoop 2.10.1's) on JDK 17. Plan runs one of these tests alone to tell which.
  3. **The real run fails end to end.** With the server and the job on JDK 17, `sales-20261113.csv` and `sales-20261115.csv` both end `FAILED (spark-submit exited with code 1)` instead of `COMPLETED`; no report is written. `sales-bad.csv` is still rejected exactly as recorded (`Line 3: bad number (For input string: "notanumber")`). Same likely cause as group 1: the local `spark-submit` stand-in starts the job with plain `java`, without Spark's module options.
- Known differences, first draft for Plan: none may remain; all three groups are faults to fix, not behaviour to accept.

### Design (slice 1: spark-job on Java 17, beside Java 8)

Class files stay Java 8, so one build serves both jobs; only how JVMs are started on Java 17 changes.
- Module access for Spark on Java 17: Spark 3.5's own list (`org.apache.spark.launcher.JavaModuleOptions`: the `--add-opens`/`--add-exports` for `java.base` packages, `-XX:+IgnoreUnrecognizedVMOptions`). Passed through `JDK_JAVA_OPTIONS`, which the Java 9+ launcher reads and Java 8 ignores, so the JDK 8 job sees no change: in `spark-job/pom.xml` surefire `environmentVariables`, and exported by the local start scripts (`scripts/reference/capture.sh`, `scripts/java17/run-workflow-server.sh`) so the child job JVM that `LocalJvmSparkJobLauncher` starts gets it too, without touching that test helper. A JDK-activated Maven profile adding the options to `argLine` (keeping `@{argLine}` for JaCoCo) is the fallback if surefire's environment does not reach the fork.
- The ZooKeeper loss: the build's first step runs `SalesAggregatorHBaseTest` alone on JDK 17 with the module options. If it still loses ZooKeeper, compare the ZooKeeper client on the spark-job test classpath under JDK 8 and 17 (`mvn dependency:tree -Dincludes=org.apache.zookeeper`) and fix it in the build only.
- Cluster image: `docker/Dockerfile` base `eclipse-temurin:8-jre-jammy` to `eclipse-temurin:17-jre-jammy`; Spark 3.5's `spark-submit` adds the module options to driver and executors itself. The JDK 8 job's cluster run then runs Java 8 class files on Java 17, which AC4 allows (the job's class files stay Java 8, not the cluster).
- Pipeline: the JDK 17 job builds and tests the whole reactor, then runs the reference compare (server and job on Java 17), `spark35` AC2, the cluster run and `hbase2` AC2 with `AC2_JOB=jdk17`; it stays allowed to fail (slice 2 makes it required). The JDK 8 job is left as it is.

### Roadmap (each step one commit)

1. spark-job tests on Java 17: module options for the forked test JVM; the ZooKeeper loss found and fixed in the build.
2. The local job JVM on Java 17: the start scripts pass the module options; the reference compare passes with server and job on Java 17.
3. The Docker Spark cluster image on Java 17.
4. The JDK 17 job runs the whole reactor and every lasting check (Test design adds this card's acceptance checks first).
5. README: the local setup says the job runs on Java 8 or 17.

Recipe: no codemod applies (no source change); the options come from Spark's own list, not hand-picked.
